## Starting point (main `d408fd7`)

What exists and is reused:
- **SFT format and masking (decision 023):** `soe/trainer/sft/data.py` encodes prompt and completion
  apart and appends `<|im_end|>`. TRL gets `input_ids` + `completion_mask`; labels outside the mask
  are −100 (container test `tests/trainer/sft/test_masking_in_container.py`). Examples above
  `sft.max_length` are dropped and counted, never truncated. The prompt is the suite's template in
  the chat template with `enable_thinking=True` (decision 006).
- **SFT worker:** `soe/trainer/sft/trainer.py` runs TRL 0.27 `SFTTrainer` with Liger's fused
  cross-entropy (`skip_logits=True` in every forward), gradient checkpointing, batch size 1 per GPU,
  no packing, `prediction_loss_only`. The F32 tensors of the checkpoint (linear-attention gate norms)
  are restored after loading. Rank 0 exports through the RL export's steps
  (`soe/trainer/rl/export.py`: base layout and dtypes, vision tower checked equal to the base, mtp
  copied, the base's config/tokenizer/chat template, `soe_export.json`).
- **Launch:** `slurm/train.sbatch` dispatches `algorithm: sft` configs to `soe.trainer.main_sft`.
  That script records job segments (`segments.jsonl`), checks the GPU count and writes `DONE`.
- **Hand-off proven on 2B (M1.8):** the dev SFT export loads in `main_eval` and as a verl
  `init_checkpoint` (2-step GRPO smoke, job 3223897).
- **Dev SFT data builder:** `examples/data_preprocess/m1_sft_dev_data.py` turns correct, stopped
  base-model samples (`SampleRecord`s) into `SftExample` lines, keeps exactly one `</think>`, splits
  by problem and reports hashes, but no text. This is the same transformation the recommended
  M2 source needs (D1).
- **Sharded base-model sampling over a problem list:** `examples/data_preprocess/m0_hard_subset.py`
  (`run_sample`, `sample_shard`) and `main_eval --stage sample` (shard claiming, `SampleRecord`
  output, any 1-GPU type).
- **Contamination method (decision 011):** `scripts/contamination_report.py --train <path under
  $SOE_DATA>` lists every pair sharing ≥ 20% of 13- or 8-grams with *every* suite problem set
  (Levels A, B, C1, C2) and classifies it E/R/V with a same-answer flag. The deletion options and
  the hand-review file format are in `docs/reports/m0_train_v3_review.json`.
- **Evaluation:** `main_eval` (sample + report stages, `plan.json` pinning, hard tier at 64 samples
  in every full evaluation), `scripts/compare_eval.py`, `scripts/transitions.py`. Base reference:
  `docs/reports/qwen35-4b-base_soe-eval-v3_report.json`, per-problem results only on FASTER
  (`$SOE_DATA/eval/qwen35-4b-base_soe-eval-v3/`).
- **RL from a checkpoint:** `main_rl.model_path` loads `$SOE_DATA/<init_checkpoint>`;
  `train_to_stop` (decision 020 revision) is CPU-tested and has never run on GPUs.
- **Shared 4B base config (decision 025):** `examples/grpo_trainer/m1_throughput_bf0_qwen35-4b.yaml`
  is the reference for every 4B RL config; learning rate, warmup and weight decay are placeholders
  (1e-6, 10, 0.0).
- **Pins (decision 025, frozen until M9):** image `soe.sif` sha256 `15824634…7196`, torch
  2.11.0+cu130, vLLM 0.24.0, verl 0.9.1, transformers 5.9.0, TRL 0.27.0, peft 0.21.2,
  accelerate 1.15.0, liger-kernel 0.8.5, flash-linear-attention 0.5.2, flash-attn 2.8.3.

What is missing (checked in the code, not assumed):
1. **Full-BF16 SFT does not exist.** `ExperimentConfig` refuses SFT unless `training_mode:
   lora_bf16` ("SFT supports lora_bf16 only so far"). The worker requires a `lora` block, wraps the
   model with peft, and trains with DDP: every GPU holds the full model. In full BF16 with FP32 master
   weights and AdamW (D6), that is about 16 B/param, about 70 GB, which does not fit one 48 GB A40.
   The full-BF16 path needs sharding. **DeepSpeed is not in `uv.lock`**, and the image is frozen
   (decision 025), so the only route that keeps the image is FSDP2 through accelerate 1.15, which
   TRL/transformers already use.
2. **No SFT checkpoints and no resume.** `save_strategy="no"`. `main_sft` refuses a run directory
   that already has a job segment ("SFT resume is not supported yet"), so a chained successor
   would fail at once. The only output is one merged export at the end of training.
3. **No full-model SFT export.** `export_merged` asserts a `lora` block and merges adapters. Full
   SFT needs the `training="full"` path (`check_trained(is_lora=False)`, which also proves that the
   vision tower is untouched). The vision tower must be frozen explicitly (decision 019 did it for
   verl's actor, not for TRL).
4. **No SFT data.** Nothing has chosen, built or decontaminated the 25K–50K trajectories. The dev
   data (424 examples, 4B-Base text on 147 RL-train problems) is wiring only.
5. **The SFT-pool contamination check has a gap.** `contamination_report.py` compares against suite
   sets only. Overlap with RL train v3.1 and the RL validation split (D2) needs a second reference
   set. The script is also fixed to `Problem` records (question + answer), so an SFT pool is checked
   at the problem level.
6. **The base reference cannot be re-scored under a new suite.** `main_eval --stage report` calls
   `write_or_check_plan`, which exits when `plan.json` names another suite. `run_report` exits on
   "samples for problems outside the plan", so v3 samples of a newly excluded problem would stop it.
   A re-score path that reads the v3 shards and writes a v4 report is needed.
7. **The frozen-start rule is only "not null".** `_check_standing_rules` requires
   `init_checkpoint is not None` for non-development RL/DPO configs. Any path passes, and nothing
   checks a hash at launch.
8. **Chained successors lose the job name.** `chain_next_job` (`slurm/common.sh`) passes no
   `--job-name`, so every successor takes `train.sbatch`'s `#SBATCH --job-name=soe-train`. M1's
   accounting had to attribute two such jobs (36.2 GPU-h) by hand (`docs/report/m1.md` 2.9).
9. **Carried from M1, not yet done:** shared RL learning rate, warmup and weight decay (decision 025:
   "fixed before M3 screening"). A CPU test that 4B algorithm configs differ only in their
   decision-001 switches. Dr.GRPO's constant `loss_scale_factor`. Dr.GRPO, DAPO and RS-GRPO are not
   wired yet: `verl_overrides` raises "wired in M3; M1 supports grpo only".
10. `ROADMAP.md`'s status column is stale (M0 "in progress", M1 blank).

## SFT data: the options (decision D1)

The plan asks for "25K–50K verified reasoning trajectories" and does not name a source. Whatever is
chosen, the trajectories must:
- render in decision 006's format: the suite prompt in the chat template with an open `<think>\n`,
  then `reasoning</think>` and the answer with a `\boxed{}`, then `<|im_end|>`;
- carry assistant-only loss (decision 023);
- fit 18,432 tokens (2,048 prompt + the 16,384 cap), dropped otherwise, never truncated;
- be verified by **our** verifier: `score_response` with the decision-008/010 rules against the
  source's gold, re-run here regardless of what the source claims;
- have their problems pass the decision-011 check against Levels A, B, C before SFT (M2.3).

Facts used below. 4B-Base on RL-train problems (format probe, decision 006): accuracy 58.5% in
thinking mode, 36% truncated at 16,384 tokens, every stopped sample boxed, mean length about 9.4K
tokens. Stopped samples therefore average about 5.5K tokens (computed: (9,400 − 0.36 × 16,384) /
0.64). One A40 samples 1,823 tokens/s at the suite's settings (`m0_eval_gpu_rates.json`).

**Recommendation: (c)**, rejection sampling from Qwen3.5-4B-Base on DeepMath-103K problems that
are disjoint from RL train v3.1 and pass the decision-011 check, with 4 samples per problem at the
suite's sampling (temperature 0.6, top-p 0.95, FP8 KV, 16K cap, thinking mode, a seed different from
evaluation's 0 and selection's 1). Keep at most 2 distinct correct, stopped completions per problem
with exactly one `</think>`. Target the low end, 25K trajectories (D3), because Lane B, not Lane A,
limits the schedule (G0). Reasons:
- It is the only option where the SFT checkpoint holds no capability from outside the model
  family, so "RL expanded what the model can solve" stays a statement about RL.
- The format is exact (the base already writes it), verification is the evaluation verifier, and
  lengths respect the cap by construction.
- The cost is about 1.2–2.4 full evaluations on Lane B, on GPUs that are otherwise idle while M2's
  Lane A work waits for data.

The second choice is (a) with DeepMath-103K's R1 solutions (zero GPU, least overlap with our RL
pool). It suits the study if you prefer the literature's "distilled start". The report would then
have to treat SFT as importing R1's capability.

### M2.6 Full-BF16 SFT path (decision 028)
- Goal: `main_sft` trains 4B in the G0 mode, checkpoints every 2–4 h, resumes in a chained job,

- Work (keeping decision 023's format, masking, length rule and Liger forward):
  - **Sharding:** FSDP2 through accelerate 1.15 / transformers 5.9 (`fsdp="full_shard
    auto_wrap"`, `fsdp_config.fsdp_version: 2`), decoder layers as wrap units. DeepSpeed is not in
    the image. The `model_path`/run machinery stays as is.
  - **Precision (D6):** load the model in FP32, so master weights, gradients and AdamW states are
    FP32. Compute in BF16 (`bf16=True`, FSDP mixed precision BF16 parameters, FP32 reduce). Then
    the F32-restore step is unnecessary, and the export writes the base's dtypes.

    switch; the Trainer flag double-wraps under FSDP). Batch size 1 per GPU and no packing (packing
    the gated-delta-net layers needs `cu_seqlens` support that TRL's padding-free path does not
    guarantee for Qwen3.5).

    scheduler and sampler position.

    checkpoint (`resume_from_checkpoint`), records `resumed_from_step`, and chains through
    `train.sbatch` (`CHAIN_LEFT`). Each step logs the example ids it trained on, so the data order
    can be checked across a resume.

### M2.9 Pre-registered SFT recipe and run-#2 rule (decision 029)
- Goal: fix the recipe of run #1 and the meaning of "the recipe needs adjustment" before run #1's
  results exist.
- Lane / GPUs: local.
- Recipe (proposal, D5; not tuned here): full BF16 (decision 025), 1 epoch, AdamW, learning rate
  1e-5, cosine decay to 0 after 3% linear warmup, weight decay 0.0, gradient clip 1.0, global batch
  32 sequences (4 GPUs × 1 × 8 accumulation steps), `max_length` 18,432. Seed 1.
- **Run-#2 rule (proposal, D6).** Run #2 happens if and only if one of these holds. Each is
  measured on the RL validation split (256 problems, decision 012) × 16 samples at the suite's
  sampling, for both base and SFT (M2.11), or on training logs; never on Levels A, B or C:
  1. **Training failure:** a NaN/Inf loss, or a final-quarter mean training loss not below the
     first-quarter mean, or the SFT validation loss (500 held-out pool problems) rising at both
     evaluations after the first.
  2. **Format failure:** fewer than 98% of SFT's stopped validation samples contain exactly one
     `</think>` and a `\boxed{}` answer.
  3. **Truncation not reduced:** SFT's truncation rate on the validation split is not below the
     base model's.
  4. **Collapse:** SFT pass@1 is below base pass@1 by more than 2 paired standard errors
     (bootstrap over problems), or SFT pass@16 is below base pass@16 by more than 2 paired standard
     errors (coverage lost, risk 2).
  The run-#2 change is also fixed now. For 1 or 4: learning rate ÷ 3, everything else unchanged.
  For 2: fix the data rule that let the format through, then rebuild. For 3: drop kept traces above
  the 90th length percentile. At most one run #2. Anything else gets a decision memo, not a third
  run.

## Risks and open questions (items marked ⚠ could confound the later algorithm comparison)
1. ⚠ **Imported capability.** With options (a), (b) or (d), SFT carries a teacher's capability, and
   RL from it can look like expansion when it is finished imitation. Option (c) removes this; with
   any other choice, the report states it in the methods and reads expansion only against the
   base reference.
2. ⚠ **SFT narrowing coverage.** Rejection-sampling SFT can raise pass@1 and lower pass@16. RL
   "expansion" relative to SFT could then just be recovery of the base model's coverage.
   Mitigations: transitions are always reported against both base and SFT, and criterion 4 of the
   run-#2 rule bounds the loss.
3. ⚠ **SFT/RL problem overlap.** If SFT has seen correct solutions to RL problems, more GRPO groups
   are all-correct (zero variance, no gradient), and train-set "unsolved→solved" counts mix SFT and
   RL. D2 makes the pools disjoint, checked with the decision-011 method (M2.3).
4. ⚠ **Length shift.** Selecting stopped samples biases SFT toward shorter traces (mean about 5.5K
   against the base model's 9.4K). This changes RL throughput and memory from M1's measurements
   (G0 triggers) and turns truncation into a major source of base→SFT transitions (decision 006).
   M2.14 measures the RL side; M2.13 splits transitions by truncation.
5. ⚠ **Level C leakage through sources built after the C2 contests.** DeepMath and OpenMathReasoning
   (April 2025) postdate HMMT Feb 2025, and contest problems often reach AoPS soon after a contest. Every
   source gets the n-gram check and the date table, and those pairs are read even below 20%.
   Level C is never used to choose anything in M2 (the run-#2 rule uses the RL validation split).
6. ⚠ **Suite drift.** v4 must exist before any SFT checkpoint is evaluated. Every M2+ comparison is
   v4 against v4, with the base re-scored, never re-sampled. M1's development evaluations stay on
   v3 and out of conclusions.
7. **Untested stack path.** TRL 0.27 + FSDP2 + transformers 5.9 on Qwen3.5's hybrid layers in FP32
   master mode has not run here. M2.7 runs it on 2B first; M2.8 is a bounded 4B check. A blocking
   bug that needs a library change would reopen decision 025.
8. **Self-trace quality.** Correct answers can come from wrong reasoning, especially on
   integer-answer problems. Kept traces need a stop, a box and one `</think>`. 50 traces are read
   by hand (M2.5), and the count of flawed ones is reported, not hidden.
9. **Difficulty skew.** Correct-only selection keeps more traces from easy problems. Per-difficulty
   counts go into `m2_sft_data.json`. The ≤ 2-per-problem cap limits the skew; no re-weighting is
   planned.
10. **One SFT seed.** Every RL run shares one SFT checkpoint, so M6's seed spread never includes SFT
    variance. The report says so; a second SFT seed is out of the plan's scope.
11. **Lane B capacity.** M2 adds 89–358 A40-h of sampling that G0's schedule did not price; it
    overlaps Lane A waiting time, but it delays M3's preference-data start if sampling runs long.
12. **Scratch space.** A 4B full-BF16 SFT checkpoint with FP32 optimizer state is about 70 GB (two
    kept), plus SFT samples. Quota checked in M2.0; M1.10/M1.11 leftovers per D11.
13. **fc098 availability.** Run #1 and the smoke wait for fc098 (D13 of M1: wait; 2×A100 only on
    your request). M2's Lane A work is short, so waiting is the right default.
14. **Hard subset and v4.** The excluded problem is not in the hard subset, so the hard tier (233
    problems in the v3 reference) is unchanged; the CPU re-score test confirms it.
