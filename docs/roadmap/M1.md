## Starting point (main `6e1baf6`)

What exists and is reused:
- `soe/trainer/config/experiment.py`: `ExperimentConfig` (Pydantic, `extra=forbid`) with the
  standing-rule validators (frozen SFT start, QLoRA dev-only, DAPO/RS-GRPO-only switches, clip
  consistency, rollout-token budget). One example, `examples/grpo_trainer/m1_dev_qwen35-2b.yaml`.
- `soe/utils/run.py` + `run_card.py`: run directories with a frozen config copy, `run.json` (commit,
  config sha256, seed, host, GPUs, library versions) and `efficiency.json` (`RunEfficiency`).
- `slurm/train.sbatch` + `slurm/common.sh`: dirty-tree refusal, `CHAIN_LEFT` chaining with
  `SOE_EXPECTED_COMMIT`, resume through `RUN_DIR`, `DONE` marker. Never run on FASTER yet.
- `soe/workers/reward_manager/math_reward.py`: verl `compute_score` hook over
  `soe.utils.reward_score.math_verify.score_response` (decisions 008, 010); one CPU test.
- `soe/workers/rollout/{chat.py,vllm_sampler.py}`: the evaluation sampler. It is text-only
  (`language_model_only=True`), stops on `<|im_end|>` (248046) plus EOS (248044), takes
  `kv_cache_dtype` and renders prompts with `enable_thinking`.
- `soe.trainer.main_eval`: already accepts a local checkpoint directory (`pinned_revision` returns
  None for a directory), so RL checkpoints can be evaluated once they are exported to HF format.
- `soe/utils/metric/{pass_at_k,transitions,eval_tables}.py`: unbiased pass@k, transitions, tables.
- Pins (`uv.lock`, image `soe.sif` sha256 `15824634…7196`): verl 0.9.1, vLLM 0.24.0,
  torch 2.11.0+cu130, transformers 5.9.0, TRL 0.27.0, peft 0.21.2, Ray 2.59.0,
  flash-linear-attention 0.5.2, accelerate 1.15.0, liger-kernel 0.8.5. M1 plans no upgrade.

What is missing:
- `soe.trainer.main_rl` raises `NotImplementedError`. `soe/trainer/rl/` does not exist (no
  `verl_overrides.py`, no `core_algos.py`), and there is no `main_sft` or any TRL code.
- No verl-format data. verl reads parquet with a `prompt` message list. The dev YAML points at
  placeholder paths (`datasets/rl/dev_*.parquet`) and still has `max_response_tokens: 4096`.
- No in-loop validation set is defined anywhere (the plan only says "a small in-loop pass@1
  validation set"). See decision D1.
- No checkpoint export (verl FSDP shards → HF safetensors for `main_eval`), no checkpoint manifest,
  no metrics file, no `tests/special_e2e/`, and no torch-dependent tests (CI is CPU-only and does
  not install torch).

Found in the pinned verl 0.9.1 wheel. Each of these breaks RL silently if left alone:
1. **Stop tokens.** verl's vLLM server builds its generation config from temperature, top-p, top-k
   and `max_new_tokens` only, and sends no `stop_token_ids`. The staged Qwen3.5 checkpoints have no
   `generation_config.json`, and the tokenizer's EOS is `<|endoftext|>`. Without a fix, every rollout
   runs past `<|im_end|>` until it hits the 16K cap.
2. **Truncated responses get reward.** The naive reward manager passes the decoded response to
   `compute_score` without saying whether it was cut off. A truncated response with a `\boxed{}`
   would score 1, while evaluation counts it as incorrect (decision 004).
3. **No `kv_cache_dtype` or `language_model_only` key in the rollout config.** Both must go through
   `actor_rollout_ref.rollout.engine_kwargs.vllm`, which verl forwards to vLLM unchanged.
4. **`trainer.use_v1: true` is the default** (new trainer; v0 is deprecated). It saves only every
   `save_freq` steps, and it neither saves on SIGTERM nor offers a time-based trigger.
5. **`actor.fsdp_config.model_dtype: fp32`**, so "full BF16" by default means FP32 master weights
   and Adam states, about 16 bytes/parameter (see decision D6).
6. **LoRA `target_modules: all-linear`** also matches the vision tower's linear layers, unless they
   are excluded (`exclude_modules`).

### M1.5 Resume, chaining and the kill-and-resume test
- Goal: a killed job resumes from its latest checkpoint with continuous metrics. This is exit
  criterion 2.
- Lane / GPUs: B, 2×A40 on fc096 or fc097. Output: `docs/reports/m1_resume_test.json`, and the `train.sbatch` /
  `main_rl` resume path (`trainer.resume_mode=auto`, `default_local_dir=runs/<id>/checkpoints`).
- Method:
  - the same dev config runs twice: an uninterrupted **control** run (12 steps, save every 3) and a
    **test** run started with `CHAIN_LEFT=1`;
  - the test run is killed with `scancel` after step 8. The chained job resumes from step 6;
  - the metrics writer keeps the last record per step, so the replayed steps 7–8 replace the lost
    ones.
- Acceptance (my reading of "identical metrics continuity"; D12):
  - step numbers and cumulative rollout tokens are continuous;
  - the optimizer step and LR schedule continue from the checkpoint;
  - the prompt ids of steps 7–12 equal the control run's (dataloader state restored);
  - the first post-resume reward, entropy and grad norm fall within the control run's step-to-step
    spread;
  - `run.json` records both job segments with their GPUs;
  - the chained successor was pinned to the same node (`scontrol show job` shows `ReqNodeList` equal
    to the first job's node, and the same `gres`);
  - a resume started by hand on other hardware is refused by the `hardware.txt` guard.
  - Bitwise-equal metrics are not expected: vLLM batching is not deterministic.

### M1.7 Unit tests for what silently breaks RL
- Goal: hand-computed toy cases pin the four failure points, the way the verifier tests pin the
  scorer.
- Lane / GPUs: local. Torch-dependent tests run in the container on a FASTER CPU node (D8). Output:
  `tests/trainer/rl/*`, `tests/workers/reward_manager/*`.
- Cases:
  - **loss masking and aggregation:** prompt and padding tokens get zero weight; `token-mean`,
    `seq-mean-token-mean` and `seq-mean-token-sum-norm` match hand-computed values on two
    unequal-length sequences;
  - **advantages:** GRPO equals (r − group mean) / (group std + ε). A zero-variance group gives zero
    advantage (no NaN), and Dr.GRPO drops the std. RS-GRPO is added in M3;
  - **reward wiring:**
    - correct, wrong, no box, truncated (reward 0) and split answers (decision 010);
    - the answer is taken after the last `</think>`;
    - reward equals `main_eval`'s verdict on 200 fixtures. The fixtures are drawn from RL-train
      problems only, since evaluation text stays out of git;
  - **checkpoint resume:** manifest dedupe, keep-last pruning and run-dir resume selection on CPU.
    The GPU half is M1.5.
- Acceptance: each test fails on a deliberately broken version (for example, mask off by one,
  std without ε, truncated rewarded). This is checked once by hand and recorded in the PR.

## Risks and open questions (items marked ⚠ could confound the later algorithm comparison)
1. ⚠ **Stop tokens in verl rollouts.** If `<|im_end|>` is not a stop token, every response runs to the
   cap, the reward reads text past the turn end, and lengths and truncation are meaningless. Fixed
   and tested in M1.3.
2. ⚠ **Truncated responses rewarded.** If truncated responses are rewarded, RL optimises a different
   target from the one evaluation measures. M1.3 sets the reward to 0 when the response hits the cap
   (D4). DAPO's overlong shaping in M3 sits on top of this, the same for its ablation.
3. ⚠ **FP8 KV mismatch (decision 009).** Rollouts sample with an FP8 cache; the trainer recomputes
   log-probs in BF16. Importance ratios and clip fractions carry this gap, and algorithms with
   different clipping (DAPO's Clip-Higher) react differently. M1 measures the gap; G0 fixes rollout
   correction on or off, the same for every algorithm.
4. ⚠ **Vision tower.** FSDP wraps the full multimodal checkpoint. LoRA `all-linear` would also adapt
   the vision linears, and full fine-tuning would give them Adam states (memory, and possible
   drift). M1.1/M1.3 exclude and freeze it, and check the trainable-parameter count.
5. ⚠ **Linear-attention numerics.** The training forward uses verl's Qwen3.5 packed-sequence patch
   (fla `chunk_gated_delta_rule`); vLLM uses its own kernel. A mismatch shows up as a log-prob gap
   even at step 0. Checked in M1.3.
6. **LoRA in vLLM for Qwen3.5's linear-attention layers** may be unsupported. In that case verl must
   merge weights before each sync, which costs time and changes the LoRA cell's throughput, not its
   math. M1.10 records which path ran.
7. **Base-model lengths in the study.** 4B-Base averages about 9.4K tokens on RL-train problems, with
   about 35% truncated; the SFT model's lengths are unknown. Memory and throughput are therefore
   measured on the long side. G1 re-checks throughput on the first M3 steps.
8. ⚠ **Hardware heterogeneity.** A100 (sm80) and A40 (sm86) run different kernels (FlashInfer with
   FP8). A fallback block also runs on 2 GPUs instead of 4: different data-parallel size, rollout
   replicas, micro-batching and possibly offload. The algorithm and global batch stay the same, but the
   numerics do not. Any block that moves follows D13, the report says which seeds ran where, and the
   seed spread then includes a hardware difference.
9. **Queue risk in M1.** fc098 is often used by another user, and the memory study runs only there, so
   M1's critical path waits on fc098. A100s are not used unless you request them.
10. **Scratch space.** A 4B full-BF16 checkpoint with FP32 optimizer state is about 70 GB, and each
    HF export about 9 GB. Over about 9 full runs with about 20 checkpoints each, that is about 1.6 TB
    of exports. Check the quota (`showquota`) before M3; keep only `keep_last` FSDP shards.
11. **verl v1 trainer is new.** Pin `use_v1=true` explicitly; any behaviour we rely on (dataloader
    state on resume, `filter_groups` for DAPO in M3) gets a test rather than an assumption.
12. **Budget.** The estimate is ≈ 129–186 GPU-h (A100 cells optional). The plan's 100–200 cap was
    lifted on 2026-10-28, so nothing is cut.
13. **Exit criterion wording.** I read "identical metrics continuity" as continuity (D12); bitwise
    equality would need deterministic vLLM kernels.
14. ⚠ **Single-node dependence on fc098.** All of Lane A rests on one node:
    - its 4 A40s are shared with another user;
    - FASTER composes GPUs onto nodes over the Liqid fabric, so the administrators could recompose or
      drain fc098;
    - a node fault stops the whole lane.
    Pinned chained jobs wait rather than move, which is correct for the comparison but can idle the
    lane for days. Hence a fallback rule fixed in advance (D13), and `train.sbatch` refuses a run that
    resumes on other GPUs (`hardware.txt`).
15. **Lane B capacity from M3.** (Also: other users hold single A40s on fc096 and fc097, so dev
    pairs can wait hours; seen 2026-10-28.) With the A40s taken by Lane A and the development pairs, the 16-GPU
    QOS cap leaves about 8 sampling workers (6 while an A100 fallback or parallel seed runs). That is
    4 A30 plus 4 A10.
    - From the M0 FP8 run (90.3 worker-h per full evaluation on an A40/A30/A10 mix), an A30/A10-only
      pool needs about 104 worker-h per full evaluation, about 13 h wall-clock on 8 workers.
    - M3's 12–20 screening-checkpoint evaluations are then about 156–260 h, and preference generation
      (15K–30K prompts × 4–8 samples) another 15–62 h, against about 336 h in M3's two weeks.
    - The knobs are those of decision 004: which checkpoints get the full suite (G1), and pausing a
      development pair during evaluation peaks, never the length cap. This is an estimate scaled from
      M0 throughput, not a measurement.
16. ⚠ **Comparison blocks, not seeds.** The ablations (M7) are compared with the seed-1 DAPO and
    GRPO runs (M5), and DPO (M4) with the seed-1 RL runs. A "whole seed" rule therefore has to treat
    each comparison block as the unit (listed in the G0 outline). Otherwise an ablation could end up
    on other hardware than the run it is subtracted from.
